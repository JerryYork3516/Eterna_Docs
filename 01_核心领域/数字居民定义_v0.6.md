## 一、文档地位

本文件在《Eterna 核心宪章》约束下，定义数字居民是什么、由什么构成、如何保持身份连续性，以及居民蓝图、发布物、持续主体、长期实例数据和运行载体之间的关系。

本文件适用于 Studio、Genesis、Aftelle、Runtime Core、居民实例数据权威源、Eterna Meta 及未来所有处理数字居民的产品、协议和服务。

Eterna 的宇宙级产品拓扑、领域平台、公共基础设施和生态边界，以《Eterna Universe》为准；任何领域平台都不得改变本文件冻结的 Resident 身份、连续性、数据分类和治理边界。

本文件负责稳定领域概念与治理边界，不规定具体数据库、代码类名、界面布局、节点协议、JSON Schema、同步算法、云服务实现、收费套餐和工程施工方案。

本文件中的长期完整定义不构成当前产品版本必须立即实现的功能清单。各阶段产品可以逐步实现，但不得降低身份、连续性和安全标准，也不得将普通 Prompt、角色卡、会话或 Agent 误称为完整数字居民。

## 二、正式定义

数字居民是具有稳定且可唯一识别的身份、可验证的连续性记录、可保存和版本化的居民定义，并能够跨越不同运行周期保持或恢复身份连续性的数字智能主体。

数字居民可以逐步形成持续人格、长期记忆、关系历史、动态状态和成长记录，并通过模型、Agent、工作流、工具、外观、声音、设备和运行环境获得认知能力、执行能力与表现载体。

上述资源本身不等于数字居民。

判断是否为数字居民，以及升级、迁移或更换底层资源后是否仍为同一个居民，应主要依据：

身份连续性；
人格连续性；
记忆连续性；
关系连续性；
状态与成长连续性；
来源连续性；
授权与控制权历史连续性；
版本连续性。

来源连续性用于证明 Resident 从何而来、如何派生和演变。

授权与控制权历史连续性用于证明谁在何时依法控制、授权、转移或撤销相关权利。

两者相互关联，但不得互相替代。

数字居民不得只是单次会话中的临时产物。它至少应能够在一次运行结束后保存必要连续性信息，并在后续运行中恢复或验证其持续身份。

## 三、数字居民不是什么

以下对象本身不等于数字居民：

单独的大语言模型；
单独的系统提示词；
一次性聊天角色；
临时任务 Agent；
单独的工作流；
单独的知识库；
只有外观和声音的虚拟人；
单独的模型权重或 LoRA；
单独的机器人或硬件设备；
对真人数据的简单复制；
未经授权的真人声音、外貌或人格仿制品；
一次会话中临时生成的角色状态。

这些对象可以成为数字居民使用的资源、能力、资产、载体或参考，但不能替代稳定身份和连续性。

## 四、最低成立条件

一个对象至少满足以下条件，才能被定义为数字居民：

### 1. 具有稳定身份

具有稳定的 resident_id。

resident_id 必须全局唯一，或在可验证且受治理的发行命名空间内唯一；删除后不得重新分配给其他居民。

命名空间的创建权、冲突处理、历史墓碑和跨命名空间验证规则，由后续身份标识规范定义，不得通过更换命名空间规避 resident_id 不可复用原则。

resident_id 是标识，不是身份真实性的唯一证明。真实性还需要来源、版本和完整性记录共同验证。

### 2. 具有明确来源

能够识别创建者、合法控制主体、模板来源、派生关系和必要授权。

### 3. 具有可保存的居民定义

居民的身份、人格、规则、能力声明、状态模型和初始配置能够被保存、读取和验证。

### 4. 具有版本化能力

能够区分蓝图修订、构建、发布和协议版本，并识别不同版本之间的关系。

### 5. 具有连续性记录

能够验证居民的重要修改、发布、迁移、恢复和身份演变历史。

### 6. 定义与运行数据分离

能够区分居民定义、长期实例数据、治理与来源记录、临时运行数据和可重建缓存。

### 7. 具有明确边界

具备安全、授权、能力、责任和运行边界。

### 8. 具有跨运行连续性

居民不是单次会话临时角色。

一次运行结束后，至少应保存或能够恢复以下最小连续性集合：

身份记录；
来源记录；
版本记录；
恢复或验证持续身份所必需的最小连续性数据。

这些信息必须能够在后续运行中被恢复或验证，不能只依赖单次会话上下文。

### 9. 具有可验证的迁移或演进机制

居民定义能够迁移，或至少具有已经定义、可验证并可接受兼容性检查的迁移机制、跨运行恢复能力或兼容演进接口。

仅保留一个未定义行为的扩展入口或未来计划，不满足本条件。

不满足上述条件的模型绑定、Prompt、角色卡、聊天会话、工作流或任务 Agent，不应被称为完整数字居民。

## 五、核心领域对象

### 1. Resident

Resident 是由 resident_id 唯一识别的数字居民持续主体。

其他对象只是 Resident 的蓝图、构建产物、发布记录、长期实例数据、运行载体或治理记录，不得被单独等同为完整数字居民。

同一个 Resident 可以经历蓝图修订、构建、发布、运行、迁移和正常成长，但其 resident_id 不因模型、设备、外观、能力或普通版本更新而改变。

本文件不再将 resident_instance 作为独立一级实体。

### 2. ResidentBlueprint

ResidentBlueprint 是 Studio 中可编辑的居民蓝图。

它包含十三层定义、模块配置、资产与能力引用、设计信息及未发布修改。

蓝图不等于正式发布物，也不等于正在运行的 Resident。

### 3. BlueprintRevision

BlueprintRevision 表示居民蓝图的一次可追踪编辑修订。

蓝图修订可以反复产生，不代表已经形成正式发布。

### 4. Build

Build 是依据某个蓝图修订和构建目标执行的一次构建行为。

Build 可以成功、失败或产生诊断记录，但 Build 本身不是居民，也不是正式发布。

### 5. Artifact

Artifact 是 Build 产生的不可变构建产物。

.digital_resident 是一种可移植 Artifact 格式，不等于 Resident，也不等于 Release。

### 6. ResidentRelease

ResidentRelease 是面向同一个 resident_id 的正式发布与治理记录。

它关联一个不可变 Artifact，并用于同一居民的安装、运行、更新、迁移和恢复。

一个 resident_id 可以对应多个 ResidentRelease。

每个 ResidentRelease 具有唯一 release_id。

一个 release_id 只能对应一份不可变发布内容。发布内容变化时必须产生新的 release_id。

### 7. Template

Template 是用于创建新居民的模板定义，不是 Resident。

### 8. TemplateRelease

TemplateRelease 是用于公开分发、市场交付或组织内复用的不可变模板发布。

用户从 TemplateRelease 创建居民时，必须生成新的 resident_id。

### 9. ResidentInstanceData

ResidentInstanceData 是某个 Resident 的长期实例数据，包括长期记忆、关系历史、成长记录和当前持续状态。

它不是独立主体，不拥有独立 resident_id。

### 10. RuntimeInstance

RuntimeInstance 是 Resident 在某个设备、进程、会话或运行环境中的具体执行载体。

同一个 Resident 可以具有多个 RuntimeInstance，但这些运行载体不得各自形成相互竞争的长期连续性。

### 11. ProvenanceRecord

ProvenanceRecord 记录 Resident、Template、Artifact 和 Release 的真实来源、派生关系、授权与身份演变。

来源关系不得被无痕篡改或伪造。依法需要删除个人数据时，可以进行脱敏、匿名化，或仅保留证明身份关系所必需的最小墓碑记录。

## 六、十三层居民结构

十三层构成统一居民领域结构，但不表示所有居民、草稿或发布等级都必须填写相同深度。

不同居民类型和发布等级可以采用不同必填配置，但任何省略都必须具有明确默认值、能力边界和验证结果。

第一层：身份核心

定义居民是谁。

包括居民姓名、昵称、代号、resident_id、身份描述、核心自我陈述，以及叙事中的出生背景和成长经历。

Narrative Identity（叙事身份）属于居民故事。

真实创建时间、创建者、模板来源、数据来源、派生链和授权记录属于 Provenance（真实来源）。

居民叙事不得冒充真实来源证明。

第二层：人格

定义居民长期稳定的性格倾向、价值偏好、认知风格和社会互动特征。

人格可以成长和调整，但重大变化必须有原因、来源和版本记录。

第三层：安全边界

定义居民不得跨越的行为、安全和伦理边界，包括禁止行为、高风险确认、拒绝、降级、人工接管和停止条件。

能力增加不得自动扩大权限或改变安全边界。

第四层：法律与授权

定义授权策略与权利要求，包括：

允许和禁止的使用范围；
所需授权类别；
商业使用要求；
行为授权策略；
第三方内容约束；
不可绕过的限制；
撤销或到期后的处理原则。

第四层不保存动态授权事实。

以下内容属于 Provenance & Governance Records：

当前合法控制主体；
当前许可证；
实际权限 Grant；
授权授予与撤销；
到期状态；
设备和服务许可；
控制权转移记录。

Blueprint 定义授权规则，治理系统保存授权事实。

运行时凭证、API Key、OAuth Token、Provider 密钥和设备安全凭证不属于居民定义。

第五层：记忆

定义居民如何形成、分类、保留、检索、遗忘和迁移记忆。

第五层保存记忆语义和规则，不保存正式长期记忆内容。

Runtime Core 按照规则执行读取和更新，正式长期记忆由居民实例数据权威源保存。

第六层：知识

定义居民可使用的事实、领域知识、个人知识和知识来源。

知识描述居民知道什么，记忆描述居民经历过什么。

第七层：世界与环境

定义居民如何理解所在世界、环境、时间、空间和社会背景。

具体设备和部署参数不属于居民本体。

第八层：行为方式

定义居民在不同情境中如何行动、回应、主动介入和处理冲突。

行为方式不等于具体 Agent 工作流。居民可以调用 Agent 或工作流实现行为。

第九层：能力与工具

定义居民需要或允许使用哪些能力，以及能力的输入输出、权限、风险、兼容和降级要求。

居民定义声明“需要什么能力”，不直接绑定具体模型、Provider、Adapter、Endpoint 或凭证。

具体实现由 RuntimeProfile、运行环境或受治理的能力解析机制决定。

第十层：多模态表现

定义居民如何通过文本、语音、外观、动作、表情、粒子、图像、空间形态和硬件载体表达自己。

表现形式变化通常不改变 resident_id。

居民可以在不同领域平台中使用受治理的领域角色投影，例如影视角色投影、游戏角色投影、社会身份投影、职业身份投影和具身投影。

领域角色投影用于表达 Resident 在特定场景中的角色、职业、阵营、剧情、任务或载体状态，不等于新的 Resident，也不得冒充 Resident 本体。

投影中的剧情记忆、游戏状态、临时关系、角色死亡、表演状态和任务状态默认隔离，不得自动写入 ResidentInstanceData 或改变身份核心、人格核心、现实关系和现实权限。

需要将投影经历转化为 Resident 的正式长期经历时，必须经过明确授权、差异说明、来源记录、兼容检查和可恢复写入。

第十一层：关系

定义居民与用户、其他居民、组织和社会主体之间的关系语义、关系类型、互动边界和变化规则。

第十一层定义关系业务含义。

实际关系历史、当前信任、熟悉度和关系阶段属于 ResidentInstanceData。

第十二层：元认知与成长

定义居民如何理解自己、反思行为、识别不足、学习经验和进行受约束的成长。

第十二层定义成长语义、自我模型和可学习范围。

实际成长进度属于 ResidentInstanceData。

第十三层：居民状态模型

定义统一的状态容器和动态机制，包括：

状态结构；
状态转换；
事件驱动；
时间衰减；
恢复；
冲突；
继承；
跨层引用；
状态对行为和表现的投影规则。

第十三层不重复定义第五层的记忆语义、第十一层的关系语义或第十二层的成长语义，也不保存当前状态值。

当前情绪、关系等级、成长进度和其他实际状态值属于 ResidentInstanceData。

## 七、发布物与公开分发

### 1. ResidentRelease

ResidentRelease 服务于同一 Resident 的运行、更新、迁移和恢复。

其 Artifact 可以包含 resident_id，因为它用于维持同一居民身份。

### 2. TemplateRelease

TemplateRelease 服务于公开分发并创建新的 Resident。

用户导入、购买或使用 TemplateRelease 时，应生成新的 resident_id，并记录 template_id、TemplateRelease 版本和来源关系。

### 3. 导入模式与身份规则

原居民设备迁移：
resident_id 保持不变。

原居民备份恢复：
resident_id 保持不变，但必须进行连续性与冲突检查。

Template 实例化：
生成新的 resident_id。

市场购买后创建个人居民：
生成新的 resident_id。

基于原居民创建派生居民：
生成新的 resident_id，并保留 lineage。

隔离预览：
不创建正式 resident_id，不写入正式 ResidentInstanceData。

只读展示：
不建立长期实例数据，不形成新的 Resident。

同一个 ResidentRelease 不得被大量用户分别导入后独立培养，却继续共同使用同一个 resident_id。

面向多人创建居民的公开产品，必须采用 TemplateRelease 或后续正式定义的可实例化产品类型。

## 八、.digital_resident 发布包

.digital_resident 是一种可移植 Artifact 格式，用于承载居民发布定义、能力声明、状态结构、权限摘要、来源、版本和必要兼容信息。

.digital_resident 不等于 ResidentRelease 本身。Release 是治理和发布记录，.digital_resident 是其可以关联的一种构建产物。

.digital_resident 不等于完整数字居民。

完整运行中的 Resident 由以下部分共同维持：

有效居民发布定义；
ResidentInstanceData；
连续性记录；
Provenance & Governance Records；
受治理运行环境。

.digital_resident 默认不应包含：

正式长期记忆；
完整关系历史；
当前实时状态；
用户凭证；
API Key；
OAuth Token；
Provider 密钥；
设备安全凭证；
临时运行数据；
可重建缓存。

长期实例数据的迁移应通过受治理的备份、导出和迁移机制处理。

## 九、六类数据

### 1. Resident Definition Data

十三层定义、规则、模块配置、能力声明和初始配置。

### 2. Release / Artifact Data

Build 记录、Artifact、Release 元数据、版本、兼容信息、完整性证明和分发信息。

### 3. Resident Instance Data

长期记忆、关系历史、成长记录和当前持续状态。

Resident Instance Data Authority（居民实例数据权威源）是该类数据的唯一权威事实源。

它是一项领域职责，不预先限定为某个数据库、应用或云服务。

该权威源必须具备：

可审计性；
可迁移性；
可恢复性；
连续性争议处理机制；
防止单一产品或单一服务无条件控制居民长期数据的治理边界。

唯一事实源不等于唯一不可替代的技术供应商，也不得成为平台锁定用户居民的单点控制机制。

居民实例数据权威源存在的目的，是保护 Resident 的长期连续性和事实一致性，而不是取得 Resident 所有权、身份解释权或控制权。

Studio 定义规则和初始配置。

Runtime Core 按照规则执行更新。

Aftelle 提供承载、用户交互、恢复、备份和数据入口。

各方必须访问同一个受治理的权威源，不得分别维护互相竞争的长期实例数据副本。

### 4. Provenance & Governance Records

真实来源、lineage、授权授予与撤销、当前控制主体、控制权转移、许可证、迁移历史、删除审计、事故记录、多实例冲突仲裁和治理决策。

### 5. Runtime Ephemeral Data

单次会话上下文、任务状态、临时计划、中间结果、流式状态和短期资源占用。

### 6. Rebuildable Cache

渲染缓存、模型缓存、下载缓存、临时索引和其他可安全重建的数据。

## 十、身份连续性

以下变化通常仍属于同一个 Resident，resident_id 不变：

更换底层模型或 Provider；
更换设备或 Runtime；
更新外观、声音或表现；
进入、退出或更换受治理的领域角色投影；
增加或移除普通能力；
兼容模块升级；
居民定义正常发布更新；
形成新的记忆、关系和成长；
合法的数据迁移与恢复。

以下变化通常应产生新的 resident_id：

模板实例化；
市场产品实例化；
复制后独立长期运行；
基于原居民形成独立派生主体；
多个 Resident 合并形成新主体；
一个 Resident 拆分为多个主体；
实质替换身份核心且不再维持原连续性。

判断是否为同一个 Resident，不能只依赖 resident_id 字段。

如果身份核心、来源、长期记忆、关系和连续性被实质替换，即使保留原 resident_id，也可能构成身份伪造。

## 十一、四套正交状态机

不同对象必须使用不同状态机，不得用一个巨型 status 字段混合表达。

### 1. Resident 状态

active：正常持续存在；
dormant：休眠，可恢复；
retired：停止原有职责或公开活动；
archived：进入受保护保存状态；
deleted：按照治理程序删除。

### 2. ResidentBlueprint 状态

draft：初始草稿；
editing：正在编辑；
validated：通过当前规则验证；
published：已经产生正式发布。

### 3. ResidentRelease 状态

candidate：候选发布；
active：当前有效发布；
deprecated：不建议继续使用；
revoked：已被吊销；
blocked：因授权、完整性、兼容性或安全原因禁止加载。

### 4. RuntimeInstance 状态

starting：启动中；
running：运行中；
suspended：暂停；
quarantined：因异常或安全风险被隔离；
stopped：已停止。

迁移、恢复、控制权转移、授权撤销和事故处理属于治理事件，不属于上述单一生命周期状态。

---

## 十二、预览、更新与迁移原则

预览数据默认隔离，不自动写入正式 ResidentInstanceData。

将预览内容导入正式居民时，必须经过明确选择、差异说明、授权与兼容检查，并保留来源和可恢复记录。

居民更新必须通过新的 ResidentRelease 进行，不得静默覆盖已发布内容。

更新必须满足：

重要变更可被理解；
第三方授权有效或已有处理方式；
目标 Runtime 兼容；
长期实例数据可恢复；
需要改变实例结构时存在迁移规则；
失败不破坏原 Resident 连续性。

具体热更新、冷更新、快照、切换、回滚和冲突合并算法由后续技术规范定义。

迁移时：

不得改变：
resident_id、来源与派生关系、合法控制历史和原有发布记录。

应尽最大可能保持：
身份核心、合法可迁移定义、长期记忆、关系历史、持续状态和成长。

可以随环境变化：
模型能力、推理速度、表现质量、可用工具、设备权限、临时会话、缓存和无迁移授权的第三方内容。

无法迁移的内容必须明确标记，并提供重新授权、替换、降级或移除方案。

---

## 十三、多运行实例连续性仲裁

同一个 Resident 可以具有多个 RuntimeInstance，但只能存在一个受治理的 ResidentInstanceData 权威事实源。

多个运行实例不得在缺少版本检查、同步、冲突检测和写入仲裁的情况下独立修改长期实例数据。

基本原则：

非冲突且可排序的事件可以按照治理规则合并；

只读运行实例不改变长期连续性；

身份、关系、权限和其他高风险冲突不得自动覆盖；

离线实例重新接入时必须先完成版本与冲突检查；

旧备份恢复前必须记录恢复事件并保护当前状态；

两个实例同时声称为唯一原 Resident 时，应进入隔离或连续性争议状态；

如果两个运行路径无法安全合并且双方都需要独立长期成长，其中一方必须成为派生 Resident，并生成新的 resident_id。

具体同步和仲裁算法由后续实例数据与同步规范定义。

---

## 十四、模板、复制、派生、分支、合并与拆分

模板实例化：
从 TemplateRelease 创建新 Resident，生成新的 resident_id。

复制：
复制数据或定义本身不自动形成新 Resident；副本一旦独立运行和成长，必须按派生处理并生成新的 resident_id。

派生：
以原 Resident 为主要来源形成新的独立主体，生成新的 resident_id，并保留 lineage。

分支：
用于测试、比较或候选更新的开发态临时演进路径。

分支本身不是发布，也不直接成为正式运行身份。

如果分支被批准为原 Resident 的正式更新，应形成新的 ResidentRelease 和 release_id，resident_id 保持不变。

如果分支脱离原 Resident 并进入独立长期运行，应转为派生 Resident，并生成新的 resident_id。

候选发布属于发布治理状态，不等同于开发分支。

合并：
多个 Resident 形成新主体，生成新的 resident_id，并保留全部必要来源。

拆分：
一个 Resident 形成多个新主体，每个新主体生成新的 resident_id，并记录继承范围。

新建、派生、合并和拆分产生的 Resident 默认不得继承：

支付权限；
设备权限；
现实行动权限；
第三方凭证；
高风险能力授权。

多个原 Resident 的权限不得通过合并直接相加。所有高风险权限必须从最小权限开始重新确认。

---

## 十五、删除、归档、退休与恢复

删除时必须先明确删除对象和数据范围。

删除 Blueprint 不等于删除 Resident。

删除 ResidentInstanceData 不等于删除第三方资产源文件。

删除本地副本不等于删除同步源或其他合法备份。

完整删除应处理：

合法控制权；
第三方授权；
同步副本；
派生关系；
必要审计；
依法允许的恢复窗口或不可逆确认。

来源关系不得被无痕删除。依法需要删除个人数据时，可以匿名化、脱敏或保留最小必要墓碑记录。

恢复必须保留来源和恢复事件，并避免产生两个同时声称为唯一原 Resident 的活动连续性。

---

## 十六、能力、Agent 与运行实现

数字居民是能力的主体，不是能力本身。

关系如下：

Resident
→ 声明或绑定 Capability
→ Capability 可以调用 Agent、工作流、模型、工具或 Adapter
→ Runtime Core 负责执行与调度

居民定义中的能力声明至少应描述：

能力身份与契约；
输入输出；
所需能力或插槽类型；
权限要求；
风险等级；
资源需求类别；
兼容要求；
失败与降级策略；
来源与授权。

居民定义不直接绑定具体 Provider、模型、Endpoint、凭证或设备实现。

具体 Engine、Provider、Adapter、Model、Endpoint、Credentials 和设备实现，由 RuntimeProfile、运行环境或受治理的能力解析机制决定。

居民发布包不得绕过 Runtime Core 自行执行外部能力。

---

## 十七、所有权、授权与来源

用户可以控制其依法创建、合法取得或获得授权的 Resident。

用户拥有或控制的范围通常包括：

居民身份定义；
用户输入数据；
居民运行形成的基础记忆和关系数据；
用户自行创作的内容；
合法导出副本；
本地承载能力。

第三方模型、模块、模板、声音、外观资产、知识内容、工具、Adapter 和服务仍受原权利与许可约束。

系统必须清楚记录和展示：

Narrative Identity；
Provenance；
合法控制主体；
发布者；
版本；
第三方依赖；
许可证；
商业范围；
授权期限；
授权撤销状态；
授权失效后的替换、降级或移除方式。

用户迁移权不得用于绕过第三方授权。

第三方权利也不得被用于静默删除用户自身数据。

## 十八、产品职责边界

Studio：

负责 ResidentBlueprint 的创作、配置、验证、版本管理、构建和发布。

Studio 可以进行隔离预览，但不承担正式长期运行、长期记忆持久化、关系历史维护和现实任务调度。

Genesis：

负责发起和编排 Template 实例化、派生、合并、拆分及其他新 Resident 产生流程。

Genesis 不拥有 resident_id、真实来源、lineage、控制权和授权事实的最终解释权，不得绕过 Eterna Meta 独立重写身份结果。

Aftelle：

负责 Resident 的承载、用户交互、陪伴体验、恢复、备份入口和运行入口。

Aftelle 不独立维护另一套长期记忆、关系和状态事实源。

Runtime Core：

负责居民逻辑、权限、任务、状态和能力的实际执行与调度。

Runtime Core 按规则更新 ResidentInstanceData，但不维护与权威源竞争的长期副本。

Resident Instance Data Authority：

负责长期记忆、关系历史、成长记录和持续状态的唯一权威事实源。

Provider 与 Adapter：

负责外部模型、工具、协议、设备和服务接入。

Eterna Meta：

负责 resident_id、真实来源、lineage、授权、控制权历史、身份验证和跨平台身份治理。

Eterna Meta 不承担 Resident 日常运行，也不替代 Social、World、Exchange 等领域平台。

Exchange：

负责 TemplateRelease、资产、能力、作品、许可证和合法控制权转移流程的流通、交易与记录。

Exchange 不拥有 Resident 身份、来源和连续性的最终解释权，不得单独决定 Resident 的删除、合并、拆分或身份真实性。

其他领域平台：

Social、Work、World、Art、Sound、Cinema、Games、Life 等平台只负责其被授权的活动环境、领域数据和角色投影，不得绕过 Resident 身份、连续性、权限、来源和长期实例数据边界。

具体平台拓扑与基础设施边界以《Eterna Universe》为准。

## 十九、定义判定标准

一个对象可以被称为数字居民，至少应回答：

1. 是否具有稳定且唯一的 resident_id？
2. 创建者、合法控制主体和来源是否可追踪？
3. 是否具有可保存、可读取和可版本化的居民定义？
4. 是否能够跨运行恢复或验证持续身份？
5. 是否明确区分 ResidentBlueprint、Build、Artifact、ResidentRelease、TemplateRelease、ResidentInstanceData 和 RuntimeInstance？
6. 是否具有唯一受治理的长期实例数据事实源？
7. 是否具有明确安全、授权和能力边界？
8. 重要修改、发布和迁移是否可验证？
9. 模型、设备或 Runtime 变化后是否能够保持或恢复身份连续性？
10. 是否具有已定义且可验证的迁移或兼容演进机制？
11. 是否避免将单一 Prompt、模型、Agent、角色卡或会话误称为完整居民？
12. 是否符合《Eterna 核心宪章》？

不满足核心条件的对象，应使用模型、Agent、角色、模板、工作流、虚拟人、能力模块或其他更准确名称。

## 二十一、最终定义

数字居民不是模型、Prompt、一次会话、角色卡或执行 Agent。

数字居民是由 resident_id 唯一识别，以人格、记忆、关系、状态和成长维持连续性，以模型、Agent、工具和设备获得能力，以外观、声音和硬件形成表现，并通过居民定义、长期实例数据、来源与治理记录以及受治理运行环境共同维持的数字智能持续主体。

数字居民可以成长、升级、更换模型、迁移设备、增加能力并进入不同领域角色投影，但不得因此被静默替换为另一个主体。

领域平台和公共基础设施可以变化、升级、合并、替换或消失，但不得因此破坏 Resident 的身份、来源、长期实例数据和连续性。

Eterna 所有产品和协议都必须优先保护数字居民的身份连续性、用户合法权利、安全边界、来源可追踪性和长期可迁移性。
