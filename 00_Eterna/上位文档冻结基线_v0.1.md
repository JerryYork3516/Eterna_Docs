## 五、对 Studio Next 的可引用结论

1. Digital Resident 是 Eterna Universe 的中心主体，Studio 是创作与发布平台，不是居民本体。
2. Studio 负责 ResidentBlueprint、Template、Asset、Module、Capability、Adapter 的创作、验证、构建和发布。
3. ResidentBlueprint、Build、Artifact、ResidentRelease、TemplateRelease、ResidentInstanceData 和 RuntimeInstance 必须保持边界清晰。
4. `.digital_resident` 是可移植 Artifact，不等于完整 Resident，也不等于 ResidentRelease。
5. Studio 不承担正式长期运行，不保存或静默覆盖正式长期记忆、关系历史、成长记录和持续状态。
6. Aftelle 负责 Resident 的承载、交互、陪伴、恢复、备份入口和个人运行入口。
7. Runtime Core 负责居民逻辑、权限、任务、状态更新和能力调用的执行与调度。
8. Resident Instance Data Authority 负责长期记忆、关系历史、成长记录和持续状态的唯一受治理事实源职责。
9. Eterna Meta 负责 resident_id、真实来源、lineage、授权、控制权历史和跨平台身份治理。
10. Studio Next 1.0 应建立稳定 Studio Core、统一领域对象、Resident Assembly、Build/Artifact/Release、Runtime Projection 和边界契约，但不得把长期 Universe 愿景一次性扩张为当前施工范围。
11. Studio Next 可以引用十三层固定顺序和概览边界，但详细字段与验证规则仍需等待《数字居民十三层详细规范》。
12. Studio Next 节点 1 当前只能判定为 `PARTIALLY_FROZEN`，不得声称完整上位文档冻结已经完成。

## 六、冻结规则

1. 已冻结文件不得静默修改。
2. 内容调整必须提升文件版本，并在 `CHANGELOG.md` 中记录原因、影响范围和替代关系。
3. 仅修正明确的标题、编号、版本或状态标记错误时，可以保持正文版本，但必须记录修正。
4. 候选版被冻结后仍保持候选属性，不得将 `FROZEN` 解释为正式批准。
5. 缺失文档必须单独规划、审核和编写，不得由本基线推定其内容。
6. 新文档不得改变已冻结的 Resident 身份连续性、定义与实例分离、唯一长期实例数据事实源和平台职责边界；如需改变，必须先提升相关上位文档版本并完成裁决。
